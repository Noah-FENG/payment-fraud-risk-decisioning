# Feature sources and availability at decision time

Each row is one transaction, and the decision point is the moment that transaction arrives. A field being present in an offline file does not mean a real system would have had it at that moment. The business meaning and generating pipeline of the anonymised fields are not fully public, so this project registers its availability assumptions explicitly and tests how much the model depends on them with feature-group ablations.

## Field groups and limits of use

| Field or feature group | Source | Assumed availability at decision time | Default use and risk |
| --- | --- | --- | --- |
| `TransactionID` | Official transaction key | Available for joins and output | Key, stable ordering, traceability; never a model input |
| `isFraud` | Official label | Unknown when the current transaction is scored | Training and evaluation only; never an input, proxy key or historical statistic |
| `TransactionDT` | Official relative time | Available on arrival | Splits and relative time windows; not convertible to real dates, holidays or local night |
| `TransactionAmt`, log amount | Official amount and row-level transforms | Assumes the amount is known before authorisation | Not realised loss; abnormal, negative or non-finite values must be audited |
| `ProductCD`, `card1`-`card6`, `addr1`-`addr2` | Anonymised product, card and address attributes | Assumed available for the current transaction | Categorical; equal values do not prove the same person or card |
| `P_emaildomain`, `R_emaildomain` | E-mail domain attributes | Assumed available for the current transaction | High cardinality and missingness; a common domain is not an entity ID |
| `M1`-`M9` | Listed by the competition as transaction categoricals | Meaning and creation time not fully public | Recorded as anonymous attributes; no causal reading |
| `DeviceType`, `DeviceInfo` | Device attributes from the identity table | Assumed available at request time; coverage is incomplete | A shared device model is not the same physical device |
| `id_12`-`id_38` | Listed as identity categoricals | Creation time not fully public | Categorical codes; identity values are never imputed |
| `id_01`-`id_11`, `C*`, `D*`, `V*` | Anonymised numeric and engineered attributes | Research assumption only: "generated by transaction time" | Registered as a separate group and ablated; upstream leakage is not ruled out |
| Identity match and missing indicators | Result of the left join and the current record | Whether an identity record exists is assumed observable on arrival | Distinguishes "no identity record" from "field missing inside a record" |
| Historical proxy-relation counts, amounts, gaps | Derived in this project from raw attributes | Only `history.TransactionDT < current.TransactionDT` | No labels; transactions with the same offset cannot see each other |
| Historical fraud rate, cumulative known fraud | Needs a label-confirmation process | No reliable label-confirmation delay is documented | Excluded by default; final labels must not pose as instantly known |

Category lists come from the [IEEE-CIS data description](https://www.kaggle.com/competitions/ieee-fraud-detection/data), checked 2026-10-21. The detailed business meaning of the anonymised columns has not been verified, and a column-name prefix is not evidence of its source.

## Encoding and preprocessing contract

Missing categoricals become an explicit missing marker. Logistic regression uses a one-hot encoding fitted on the training block, with rare categories grouped and the expansion per column capped; unseen values follow the fitted encoding rule. XGBoost uses an ordinal encoding fitted on the training block, and unseen categories map to `-1`. This puts an artificial category order into the tree model, a modelling choice that must be acknowledged when interpreting results. Frequencies and category tables are never computed on all the data first.

Missing numerics take the median of the corresponding fitting block and also get a missing indicator; logistic regression then standardises with that block's parameters. During candidate search the fitting block is train; after hyperparameters are chosen, the final base model and its preprocessing are refitted together on train plus tune. Calibration, policy and final test never take part in fitting the base preprocessing. Feature construction also emits a constant `<column>__missing` column so that "complete in training, missing at prediction" can be expressed. Later blocks reuse the same fitted preprocessor and never call `fit_transform` themselves. Amounts keep their raw value and gain `log_amount = log1p(TransactionAmt)`; extreme positive amounts are not silently clipped.

If a numeric field is read as float because of CSV missing values, known categorical fields such as `card*` or `addr*` must not be treated as continuous. Amount outliers must stay visible in the audit; high-value transactions are never dropped silently.

## Historical relation semantics

Candidate keys are **proxy relationships** built from attribute combinations. For example, with `card1/card2/card3/card5/addr1` one can study whether the combination recurs; it is not a verified customer or card identifier. `DeviceInfo/addr1` likewise defines only an attribute co-occurrence.

If any required key field is missing, no proxy relation is created. Missing values are not all filled with `UNKNOWN` and then linked together. Historical statistics group equal timestamps first and accumulate only earlier groups; adding future rows must not change any existing row's historical features. The assumed availability of identity fields must be registered together with the relation features.

## Ablation and interpretation

The anonymous ablation removes, in code, every `C*`, `D*`, `V*` and `M*` field with a numeric suffix and every `id_*` field with a numeric suffix. Even where the competition lists some of them as categorical, that does not verify when they are generated upstream. The explicit device attributes `DeviceType` and `DeviceInfo` stay. The exact group definition is `features.is_anonymous`.

At least three variants are compared: XGBoost on raw transaction attributes, XGBoost with the anonymous engineered attributes, and XGBoost with strictly historical proxy-relation features. They use the same blocks, tuning-candidate budget and review capacity. A performance drop after removing the anonymous attributes shows only that the model depends on those inputs; it does not show whether they leak. Any gain from relation features must be read together with the results for new proxy relations, isolated records and missing identity.

SHAP describes how the model uses its inputs. For anonymous features it is read no finer than the column or feature group. It cannot prove real customer behaviour, reveal fraud rings, or give a causal reason to decline a transaction.
